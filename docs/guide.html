AdGuard Home на каждой ноде

AGH на всех VPN-серверах с синхронизацией фильтров с одной origin-ноды. Единой точки отказа нет, ручная настройка существует ровно в одном месте, а новая нода ставится одной командой прямо с GitHub и находится синхронизатором сама.

Что получается в итоге

Добавление ноды не требует ни одной правки на origin.

Код

Скрипты, compose-файлы и шаблон конфига живут в репозитории dykomenko/adh-fleet, там же пошаговые docs/origin.md и docs/replica.md. Эта страница — обзор схемы целиком; источник правды — репозиторий.

Секретов в нём нет, поэтому ноды тянут всё прямо с GitHub. Setup key и хеш пароля лежат в .env на рабочей машине и передаются переменными окружения в командной строке установки; пароль админа — только на origin, в admin.pass с правами 600.

Адресация по формуле, а не по таблице

На тридцати нодах таблица соответствий превращается в источник ошибок. Возьмите правило, из которого адрес выводится по номеру ноды:

НодаРольСеть клиентовDNS клиентам
node01origin10.101.0.0/2410.101.0.1
node02replica10.102.0.0/2410.102.0.1
nodeNNreplica10.(100+NN).0.0/2410.(100+NN).0.1
node30replica10.130.0.0/2410.130.0.1

Адреса в оверлее назначает Netbird — их знать заранее не нужно, ноды обращаются друг к другу по именам.

Номер ноды задаёт правило firewall, а не bind-адрес

AGH слушает 0.0.0.0:53: интерфейс WireGuard появляется и исчезает при рестартах, и привязка к его адресу ломает старт AGH после перезагрузки. Из номера ноды выводится сеть клиентов, и именно она попадает в правило iptables — доступ к порту 53 открыт только оттуда.

Почему сети обязательно разные

Персональные правила в AGH привязаны к IP клиента. Если клиентские сети нод пересекутся, правила начнут срабатывать не на тех людях. Формула выше это исключает по построению.

Часть 0 · Оверлей

один раз, в консоли Netbird

Синхронизатор своей связности не приносит — ему нужно, чтобы origin дотягивался до панели каждой реплики. Оверлей закрывает это без единого конфига на нодах.

Регистрируемся на app.netbird.io и делаем четыре вещи. Все — до того, как поднимать первую ноду.

  1. Завести группы

    agh-origin и agh-replica. На них завязано и разграничение доступа, и автообнаружение реплик.

  2. Создать два setup key

    Оба с auto-assign нужной группы — тогда группа назначается сама при первом подключении и в консоли руками ничего трогать не нужно:

    • для origin — auto-assign agh-origin, хватит одноразового;
    • для реплик — тип Reusable (по умолчанию предлагается одноразовый), auto-assign agh-replica.

    Срок жизни ключа реплик выставьте с запасом — когда он истечёт, установка новых нод начнёт молча отваливаться.

  3. Отключить истечение пиров

    Иначе флот отвалится целиком

    С включённым peer expiration ноды через заданный срок потребуют повторной интерактивной авторизации — и весь парк одновременно выпадет из оверлея. На headless-серверах истечение надо снять и в настройках ключа, и в свойствах пиров. У Tailscale ровно та же ловушка с key expiry.

  4. Переписать политику доступа

    Одно правило: agh-origin → agh-replica, протокол TCP, порт 3000. Направление одностороннее — реплики не должны видеть ни друг друга, ни origin.

    Больше ничего открывать не нужно. В частности, SSH: обновление парка идёт с рабочей машины, а не с origin, чтобы компрометация origin не открывала остальные ноды.

    Дефолтное правило прячется

    Правило All → All из свежего аккаунта не отображается на вкладке Policies внутри группы agh-origin — оно оперирует группой All. Проверяйте на общей странице Access Control. Пока оно живо, сужение вашей политики не меняет ничего: все ноды видят друг друга насквозь.

Альтернативы

Tailscale устанавливается так же просто, но бесплатный Personal-план предназначен для личного использования — для коммерческого сервиса нужен платный. Self-hosted Netbird убирает зависимость от чужого control plane ценой ещё одного сервиса в эксплуатации. WireGuard руками на тридцати нодах не рассматривается: тридцать пар ключей и правка конфига хаба при каждой новой ноде.

Часть A · Origin-нода

один раз, вручную, на node01

Это единственная нода, которую вы настраиваете руками. Здесь же снимается шаблон, по которому разворачиваются все остальные.

  1. Подключить к оверлею и освободить порт 53

    bashnode01
    curl -fsSL https://pkgs.netbird.io/install.sh | sh
netbird up --setup-key <КЛЮЧ> --hostname node01 \
  --disable-dns --dns-resolver-address 127.0.0.1:5053
    Нужны оба DNS-флага

    Проверено на netbird 0.78.2. --disable-dns запрещает агенту править настройки DNS системы, но его локальный резолвер при этом всё равно поднимается и занимает порт 53 на оверлейном адресе — ровно тот, который нужен AdGuard Home.

    Освобождает порт только второй флаг: --dns-resolver-address уводит резолвер в другое место. Порт 5053 взят из примера в справке netbird; 5353 тоже работает, но это порт mDNS и на образах с avahi может конфликтовать.

    Плата — имена вида node07.netbird.cloud на нодах не разрешаются. Поэтому gen-sync.sh собирает список реплик по оверлейным адресам, а не по именам; настраивать для этого ничего не нужно.

    bashпроверка
    ss -ulnp | grep ':53 ' || echo "порт 53 свободен"
    Если агент уже стоял

    Частый случай на VPS, где netbird ставили раньше. Установщик откажется работать («NetBird service is running») и выйдет, оставив старый бинарь, а netbird up ответит «Already connected» и не применит ни ключ, ни флаги. Со старым бинарём нужного флага может не оказаться вовсе.

    Признак — порт 53 занят самим агентом: ss -ulnp | grep ':53 ' покажет netbird на оверлейном адресе.

    Лечится полной переустановкой со сбросом конфигурации. На репликах install.sh делает это сам:

    bashnode01
    systemctl stop netbird
curl -fsSL https://pkgs.netbird.io/install.sh | sh
netbird version

systemctl stop netbird
rm -f /etc/netbird/config.json
systemctl start netbird

netbird up --setup-key <КЛЮЧ> --hostname node01 \
  --disable-dns --dns-resolver-address 127.0.0.1:5053

    Старый пир останется в консоли Netbird отдельной записью — удалите его.

    Теперь освобождаем порт 53:

    bashnode01
    sudo sed -i 's/^#\?DNSStubListener=.*/DNSStubListener=no/' \
  /etc/systemd/resolved.conf
sudo systemctl restart systemd-resolved
sudo ln -sf /run/systemd/resolve/resolv.conf /etc/resolv.conf
    Третья строка обязательна

    Без неё /etc/resolv.conf продолжает указывать на 127.0.0.53, который после отключения stub-listener больше не слушает. Нода остаётся без резолвинга: перестают работать apt, docker pull и сам AGH.

    Проверяем, что порт свободен — иначе мастер установки не даст выбрать «Все интерфейсы»:

    bashnode01
    sudo ss -ulnp | grep ':53 ' || echo "порт 53 свободен"

  2. Развернуть контейнер

    Файл /opt/adguardhome/docker-compose.yml — он одинаков на всех тридцати нодах:

    yamlвсе ноды
    services:
  adguardhome:
    image: adguard/adguardhome:latest
    container_name: adguardhome
    network_mode: host
    restart: unless-stopped
    volumes:
      - ./work:/opt/adguardhome/work
      - ./conf:/opt/adguardhome/conf
    labels:
      - "com.centurylinklabs.watchtower.enable=false"

    network_mode: host обязателен: в bridge-режиме Docker занатит трафик, AGH увидит все запросы как приходящие с адреса docker-шлюза, и статистика с персональными правилами сломается.

    bashnode01
    cd /opt/adguardhome && docker compose up -d

  3. Пройти мастер установки — в последний раз

    bashрабочая машина
    ssh -L 3000:127.0.0.1:3000 user@node01

    На http://localhost:3000 задаём:

    • Веб-интерфейс — «Все интерфейсы», порт 3000
    • DNS-сервер — «Все интерфейсы», порт 53
    • Логин и пароль админа — запомните пароль, он станет общим для всего парка
    Оба поля — «Все интерфейсы»

    Если выбрать для панели конкретный адрес, мастер упрётся в самого себя: checking address 100.x.x.x:3000: bind: address already in use | 400. Во время установки AGH уже слушает 0.0.0.0:3000, и проверка доступности того же порта на конкретном адресе натыкается на его собственный сокет.

    Вторая причина важнее: адреса у нод разные, и привязка к адресу origin сделала бы шаблон непригодным для реплик. make-template.sh откажется снимать такой шаблон.

    Мастер слушает все интерфейсы, поэтому туннель на 127.0.0.1 здесь работает. После сохранения панель переедет на оверлейный адрес.

    Почему DNS на всех интерфейсах, а не на адресе VPN

    Привязка к адресу шлюза выглядит аккуратнее, но ломается на практике. Интерфейс WireGuard появляется и исчезает при рестартах: если туннель поднялся позже AGH, тот не стартует вовсе. А на свежем сервере, где VPN ещё не поднят, такого адреса в списке мастера просто нет.

    Доступ ограничивает firewall, а не bind-адрес.

    Правила — до того, как AGH начнёт слушать

    С 0.0.0.0 нода становится открытым резолвером на публичном адресе. Такие находят за часы и начинают использовать для DNS-амплификации — прилетит abuse от хостера. Примените правила прежде чем завершите мастер.

    Ставится тем же скриптом, что и на репликах — чистый iptables, без ufw: на нодах его обычно нет, а тащить пакет ради трёх правил незачем.

    bashnode01
    echo 'CLIENT_NET=10.101.0.0/24' | sudo tee /etc/adh-firewall.conf

curl -fsSL $REPO/node/adh-firewall.sh \
  | sudo tee /usr/local/sbin/adh-firewall.sh > /dev/null
curl -fsSL $REPO/node/adh-firewall.service \
  | sudo tee /etc/systemd/system/adh-firewall.service > /dev/null

sudo chmod 755 /usr/local/sbin/adh-firewall.sh
sudo systemctl daemon-reload
sudo systemctl enable --now adh-firewall.service
    Политика INPUT не меняется

    Скрипт заводит отдельную цепочку ADH-INPUT ровно для портов 53 и 3000. Правила уже настроенного на ноде VPN остаются нетронутыми, SSH и прочие порты не затрагиваются вообще — отрезать себе доступ невозможно.

    Правила iptables живут в памяти ядра и после перезагрузки исчезли бы, поэтому юнит накатывает их заново при каждой загрузке, до старта docker. Закрывается и IPv6: клиенты ходят по IPv4, а без ip6tables нода осталась бы открытым резолвером по IPv6 — это легко упустить.

    bashпроверка правил
    sudo iptables -L ADH-INPUT -n -v

    Проверка снаружи, с другой машины — ответа быть не должно:

    bashлюбой другой хост
    dig @ПУБЛИЧНЫЙ_IP_НОДЫ example.com +time=3

  4. Настроить фильтрацию

    Всё заданное здесь разъедется по репликам автоматически: списки блокировок, пользовательские правила, апстримы (например https://dns.quad9.net/dns-query с bootstrap 9.9.9.10), fallback-серверы, rewrites, сервисы и персональные клиенты.

    Персональные клиенты на тридцати нодах

    У одного человека на разных нодах разные адреса — 10.101.0.5, 10.117.0.5 и так далее. В карточке клиента AGH перечисляется несколько идентификаторов сразу, так что впишите все его возможные адреса. Если клиенты кочуют между нодами произвольно, рассмотрите вместо этого ClientID через DoT или DoH — иначе список идентификаторов станет неуправляемым.

  5. Снять шаблон конфига

    Готовый AdGuardHome.yaml с этой ноды и есть то, что превращает установку реплики в одну команду: если файл лежит на месте до первого старта, AGH не показывает мастер вовсе.

    Писать его руками не надо — снимаем с работающей ноды, подставляя плейсхолдеры вместо адресов:

    bashnode01
    curl -fsSL "$REPO/scripts/make-template.sh" -o /tmp/mt.sh
sudo bash /tmp/mt.sh

    Так вы не гадаете про schema_version и формат полей текущей версии AGH. Скрипт заменяет плейсхолдерами адреса и bcrypt-хеш пароля, а сам хеш печатает — это AGH_PASS_HASH для установки нод, положите его в .env.

    Готовый шаблон заберите на рабочую машину и закоммитьте в node/AdGuardHome.yaml.tmpl. Секретов в нём нет, поэтому лежать он может в публичном репозитории — именно из-за этого установка реплики сводится к одной команде.

  6. Поднять синхронизатор

    Одной командой — она ставит adguardhome-sync, генератор списка реплик и крон:

    bashnode01, root
    AGH_PASS='ПАРОЛЬ' sudo -E bash <(curl -fsSL \
  https://raw.githubusercontent.com/dykomenko/adh-fleet/main/origin/setup-origin.sh)

    Пароль ложится в /opt/agh-sync/admin.pass с правами 600 — это единственный секрет на origin. Сам sync.yaml руками не пишется, его собирает генератор из части C.

    Если реплик ещё нет, скрипт честно скажет об этом и выйдет: поднимите первую ноду и запустите /opt/agh-sync/sync-now.sh.

Часть B · Реплика

одна команда на ноду, 29 раз

Никакого мастера, никакого браузера, никаких правок на origin, ничего не нужно класть на ноду заранее. Одна команда на самой ноде:

bashновая нода, root
NB_KEY='...' AGH_PASS_HASH='...' \
  bash <(curl -fsSL https://raw.githubusercontent.com/dykomenko/adh-fleet/main/install.sh) 7

Единственный аргумент — номер ноды, из которого выводится вся адресация. Оба значения лежат в .env на рабочей машине: NB_KEY — setup key, AGH_PASS_HASH — bcrypt-хеш пароля админа. Это хеш, а не пароль: подсмотревший команду доступа к панели не получит.

Почему шаблон можно публиковать

В node/AdGuardHome.yaml.tmpl адреса и хеш пароля заменены плейсхолдерами, так что секретов в нём нет — и репозиторий со скриптами может быть публичным, а нода тянет с GitHub вообще всё. Никакого scp и предварительной подготовки ноды не требуется. make-template.sh откажется писать шаблон, в котором остался хоть один bcrypt-хеш.

Что выполняется на ноде:

bashbootstrap-agh.sh
#!/usr/bin/env bash
set -euo pipefail

NUM="${1:?укажите номер ноды}"
: "${NB_KEY:?не задан NB_KEY}"
: "${AGH_PASS_HASH:?не задан AGH_PASS_HASH}"

CLIENT_NET="10.$((100 + NUM)).0.0/24"

# 1. оверлей
curl -fsSL https://pkgs.netbird.io/install.sh | sh
netbird up --setup-key "$NB_KEY" --hostname "$(hostname -s)" \
  --disable-dns --dns-resolver-address 127.0.0.1:5053
NB_IP="$(netbird status --json | jq -r .netbirdIp | cut -d/ -f1)"

# 2. освобождаем 53
sed -i 's/^#\?DNSStubListener=.*/DNSStubListener=no/' /etc/systemd/resolved.conf
ln -sf /run/systemd/resolve/resolv.conf /etc/resolv.conf
systemctl restart systemd-resolved

# 3. firewall — ДО запуска AGH, иначе нода несколько секунд
#    стоит открытым резолвером на публичном адресе.
#    Отдельная цепочка только для 53 и 3000: политика INPUT
#    не трогается, правила уже стоящего VPN остаются как были.
printf 'CLIENT_NET=%s\n' "$CLIENT_NET" > /etc/adh-firewall.conf
curl -fsSL "$REPO/node/adh-firewall.sh"      -o /usr/local/sbin/adh-firewall.sh
curl -fsSL "$REPO/node/adh-firewall.service" -o /etc/systemd/system/adh-firewall.service
chmod 755 /usr/local/sbin/adh-firewall.sh
systemctl daemon-reload
systemctl enable --now adh-firewall.service

# 4. конфиг AGH из шаблона — мастер не запустится
install -d /opt/adguardhome/conf /opt/adguardhome/work
curl -fsSL "$REPO/node/docker-compose.yml"    -o /opt/adguardhome/docker-compose.yml
curl -fsSL "$REPO/node/AdGuardHome.yaml.tmpl" -o /opt/adguardhome/AdGuardHome.yaml.tmpl
# адреса не подставляются: и DNS, и панель слушают все интерфейсы,
# ограничивает доступ iptables
sed -e "s|__PASS_HASH__|$AGH_PASS_HASH|g" \
    /opt/adguardhome/AdGuardHome.yaml.tmpl \
    > /opt/adguardhome/conf/AdGuardHome.yaml

# 4. поехали
docker compose -f /opt/adguardhome/docker-compose.yml up -d

echo "нода $(hostname -s): DNS 0.0.0.0:53 из $CLIENT_NET, панель $NB_IP:3000"
echo "фильтры приедут в течение часа, либо сразу: sync-now.sh на origin"
Что происходит дальше само

Setup key назначает ноде группу agh-replica. Генератор на origin пересобирает список реплик по этой группе раз в час и подхватывает новичка, фильтры приезжают с ближайшим прогоном синхронизации. Вмешательство не требуется — а если ждать не хочется, на origin есть /opt/agh-sync/sync-now.sh.

Часть C · Автообнаружение реплик

то, ради чего всё затевалось

Список из тридцати реплик в sync.yaml руками не поддерживают. Генератор строит его по группе в оверлее и перезапускает синхронизатор, только если состав действительно изменился.

График — часовой: правила меняются редко, гонять чаще смысла нет. Когда ждать не хочется, есть ручной прогон, который пересобирает список и запускает синхронизацию сразу:

bashnode01
/opt/agh-sync/sync-now.sh
bash/opt/agh-sync/gen-sync.sh
#!/usr/bin/env bash
set -euo pipefail

PASS="$(cat /opt/agh-sync/admin.pass)"
OUT=/opt/agh-sync/sync.yaml

{
  printf 'cron: "17 * * * *"\nrunOnStart: true\ncontinueOnError: true\n\n'
  printf 'origin:\n  url: http://127.0.0.1:3000\n'
  printf '  username: admin\n  password: %s\n\nreplicas:\n' "$PASS"

  # Адреса, а не имена: у netbird отключено управление DNS, иначе его
  # резолвер занимает порт 53, нужный AdGuard Home.
  netbird status --json \
    | jq -r '.peers.details[]
             | select(.groups[]? == "agh-replica")
             | (.netbirdIp // .ip // empty) | split("/")[0]' \
    | sort -u \
    | while read -r addr; do
        printf '  - url: http://%s:3000\n' "$addr"
        printf '    username: admin\n    password: %s\n' "$PASS"
      done

  printf '\nfeatures:\n  dhcp:\n    serverConfig: false\n    staticLeases: false\n'
} > "$OUT.new"

if cmp -s "$OUT.new" "$OUT"; then
  rm "$OUT.new"
else
  mv "$OUT.new" "$OUT"
  docker restart agh-sync
fi
bashnode01
echo '5 * * * * root /opt/agh-sync/gen-sync.sh' \
  | sudo tee /etc/cron.d/agh-sync-gen
Сверьте структуру JSON

Имена полей в выводе netbird status --json менялись между версиями. Перед первым запуском посмотрите фактический вывод и поправьте jq-выражение. Для продакшена надёжнее ходить в Management API (GET /api/peers с токеном) — там контракт стабильнее, чем у CLI.

Офлайн-ноды из списка намеренно не исключаются: continueOnError позволяет синхронизатору пропустить недоступную реплику и обновить остальные, а вернувшаяся нода догонится сама. Отфильтруй мы их по статусу — пришлось бы ждать следующей пересборки списка.

Отключение ноды

Удалите пир в консоли Netbird. В течение часа он исчезнет из sync.yaml, синхронизатор перезапустится с новым составом. Ничего чистить руками не нужно.

Часть D · Клиенты

адрес шлюза своей ноды

Каждому клиенту прописывается DNS того сервера, к которому он подключается. Никаких вторых и запасных DNS: Windows и Android опрашивают перечисленные серверы параллельно, и фильтрация потечёт постоянно, а не только при аварии.

WireGuard

Push-механизма нет, адрес подставляется при генерации клиентского конфига:

iniклиент ноды node07
[Interface]
PrivateKey = ...
Address = 10.107.0.5/32
DNS = 10.107.0.1

OpenVPN

confсерверный конфиг node07
push "dhcp-option DNS 10.107.0.1"
push "block-outside-dns"

block-outside-dns нужен Windows-клиентам: без него система продолжит спрашивать DNS физического интерфейса в обход туннеля.

Часть E · Эксплуатация

Обновление парка

Тег latest означает, что момент обновления выбираете вы. Прогоняйте все ноды в одном окне, чтобы версии не разъезжались дольше пары минут:

bashрабочая машина
./scripts/fleet-update.sh node02 node03 node07
./scripts/fleet-update.sh          # или все хосты из NODES в .env
Почему не с origin

Обновление намеренно запускается с рабочей машины. Держать на origin ssh-доступ ко всему парку означало бы, что компрометация одной ноды открывает остальные — а рабочая машина доступ к нодам и так имеет. Побочный выигрыш: в политике Netbird достаточно одного порта 3000, SSH внутри оверлея открывать не нужно.

Точка отката

latest сам по себе вернуться назад не даёт, поэтому перед обновлением фиксируем образ:

bashлюбая нода
docker inspect --format '{{index .RepoDigests 0}}' adguardhome

Полученный adguard/adguardhome@sha256:… подставляется вместо тега в compose, если релиз окажется неудачным.

Бэкап

Реальная конфигурация существует в одном экземпляре — на origin. Тридцать реплик восстанавливаются из неё одним прогоном синхронизации, поэтому бэкапить достаточно её и шаблон:

bashnode01
tar czf agh-$(date +%F).tar.gz \
  -C /opt/adguardhome conf AdGuardHome.yaml.tmpl

Если реплика отстала

  • docker logs agh-sync на origin — видно, какая нода не ответила и почему;
  • проверьте, что нода вообще в списке: grep node07 /opt/agh-sync/sync.yaml;
  • проверьте доступность панели по оверлею: curl -su admin:ПАРОЛЬ http://node07:3000/control/status;
  • убедитесь, что версии AGH не разъехались далеко — в пределах патчей это безопасно, на смене минорной версии API может измениться.
Чего у этой схемы нет

Сводной статистики и единого лога запросов: и то, и другое остаётся на каждой ноде своим. Это прямая плата за отсутствие единой точки отказа — падение любой ноды задевает только её собственных клиентов, у которых в этот момент всё равно нет туннеля. Если сводная картина нужна, снимайте метрики отдельно: у AGH есть API статистики, данные с тридцати нод собираются в Prometheus или ClickHouse.

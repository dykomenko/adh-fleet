# Реплика

Одна команда на самой ноде. Ничего не нужно класть заранее, ничего не нужно
менять на origin.

---

## Установка

```bash
NB_KEY_REPLICA='...' AGH_PASS_HASH='...' \
  bash <(curl -fsSL https://raw.githubusercontent.com/dykomenko/adh-fleet/main/install.sh) HK01
```

Единственный обязательный аргумент — **имя ноды**. Под ним она появится
в консоли Netbird, так что удобно брать то же имя, что используется в остальной
инфраструктуре. Номеров помнить не нужно.

Оба значения берутся из `.env` на рабочей машине **под теми же именами**:

- `NB_KEY_REPLICA` — многоразовый setup key с auto-assign группы `agh-replica`;
- `AGH_PASS_HASH` — bcrypt-хеш пароля админа, его печатает `make-template.sh`
  на origin.

Хеш требует одинарных кавычек: в нём есть `$`, без кавычек оболочка съест часть
строки. Скрипт проверяет формат и откажется ставить ноду с чем-то, что на хеш
не похоже.

**Ключ нужен именно от реплик.** С origin-ключом нода попадёт в группу
`agh-origin`, и синхронизатор её никогда не найдёт — при этом установка пройдёт
без единой ошибки, а нода будет выглядеть рабочей.

### Если у клиентов есть адреса в туннеле

Вторым аргументом можно передать сеть клиентов — тогда 53-й порт откроется
и для неё:

```bash
... install.sh HK01 10.107.0.0/24
```

Это нужно для WireGuard и OpenVPN, где туннель раздаёт клиентам адреса.
Для Xray и Remnawave аргумент не нужен: клиенты адресов не получают, DNS
запрашивает сам прокси с этой же машины, и localhost'а достаточно.

---

## Что делает скрипт

1. ставит агент Netbird, сбрасывая состояние прошлой установки;
2. подключает ноду с явным management-url и обоими DNS-флагами, затем
   проверяет, что подключился к нужному серверу и порт 53 свободен;
3. выключает `DNSStubListener` у systemd-resolved и переводит `resolv.conf`
   на реальные апстримы;
4. ставит правила iptables и юнит, который вернёт их после перезагрузки;
5. тянет с GitHub шаблон конфига, подставляет хеш пароля и поднимает контейнер.

Готовый `AdGuardHome.yaml` на месте означает, что **мастер установки
не запустится**. Скрипт идемпотентен — повторный запуск безопасен.

---

## Что происходит дальше само

- Setup key назначает ноде группу `agh-replica`.
- Генератор на origin пересобирает список реплик раз в час и подхватывает
  новичка.
- Фильтры приезжают с ближайшим прогоном синхронизации.

Ждать час не обязательно — на origin есть `/opt/agh-sync/sync-now.sh`.

---

## Проверка

Проверяйте через адрес docker-моста — тот же, что `install.sh` прописал
в `resolv.conf`. Через адрес туннеля не надо: если туннель на ноде не поднят,
его адреса там нет и `dig` уйдёт в таймаут. Через `127.0.0.1` — тоже
не надо, этот адрес перехватывает агент netbird (см. ниже).

```bash
dig @172.17.0.1 example.com +short
```

Вернулся адрес — AGH работает. Фильтры при этом ещё пустые: шаблон их
не содержит, они приезжают синхронизацией. Запустите на origin
`sync-now.sh`, затем:

```bash
dig @172.17.0.1 doubleclick.net +short
```

Теперь должен вернуться `0.0.0.0` либо пустой ответ.

Таймаут вместо ответа при живом AGH означает, что до адреса моста не доходит
запрос: либо правила firewall устарели, либо `docker0` в состоянии
NO-CARRIER — так бывает, когда на ноде все контейнеры поднимаются
с `network_mode: host` и к мосту не подключён никто. Тогда источником пакета
ядро выбирает публичный адрес ноды, и правило по `127.0.0.0/8` его не ловит.
Лечится обновлением `adh-firewall.sh`: в нём есть правило по интерфейсу `lo`,
которое от выбора адреса не зависит.

### Проверка со стороны клиента

`dig` на ноде подтверждает только, что работает сам AGH. Дошла ли фильтрация
до клиентов — вопрос отдельный, особенно с Xray, где путь идёт через системный
резолвер ноды.

Подключитесь к ноде как обычный пользователь и откройте в браузере
**<https://adblock.turtlecute.org>** — страница прогоняет запросы к известным
рекламным и трекерным доменам и показывает, сколько из них заблокировано.

Это единственная проверка, которая охватывает всю цепочку целиком, поэтому
на новой ноде её стоит делать обязательно. Заодно она сразу покажет, если
клиент ходит мимо вашего DNS.

---

## Вход в панель

Origin и реплики в этом смысле одинаковы: обе слушают `0.0.0.0:3000`, доступ
к порту открыт только с localhost и с интерфейса оверлея.

Туннель с рабочей машины:

```bash
ssh -L 3000:127.0.0.1:3000 root@HK01
```

Дальше `http://localhost:3000`, логин `admin` и пароль парка.

Нужны две ноды одновременно — пробрасывайте на разные локальные порты:

```bash
ssh -L 3001:127.0.0.1:3000 root@HK02
```

Тогда вторая откроется на `http://localhost:3001`. Если ssh ругается
`bind: Address already in use`, локальный порт занят прошлым сеансом —
закройте его или возьмите другой.

Панель на репликах нужна только для просмотра: любые правки затрутся
синхронизацией. Настраивать — на origin.

## Подключение клиентов

**Xray / Remnawave.** Чтобы фильтрация дошла до клиентов, должны совпасть
два условия. Нарушено любое — клиенты резолвят мимо AGH, а симптом всегда
одинаковый: в журнале AGH только ваши собственные проверки.

**1. В конфиге Xray нет секции `dns`.** Пока она есть, Xray резолвит
встроенным резолвером через прописанные там серверы и системный не спрашивает
вовсе. Удаляется в шаблоне конфига в панели Remnawave — единственный ручной
шаг во всей установке.

**2. `/etc/resolv.conf` ноды указывает на адрес docker-моста.** Не на
`127.0.0.1`, а именно на адрес моста — обычно `172.17.0.1`. Это делает
`install.sh`. Проверить:

```bash
cat /etc/resolv.conf
docker exec remnanode cat /etc/resolv.conf
```

Оба должны показать одно и то же: `nameserver 172.17.0.1` и запасной резолвер
следом. Видите в контейнере другой адрес — почти всегда дело в том, что
контейнер создан раньше, чем мы поправили resolv.conf хоста: Docker формирует
файл контейнера один раз, при создании, и правка хоста до работающего
контейнера не доходит. Пересоздавать не нужно:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/dykomenko/adh-fleet/main/node/adh-live-resolv.sh)
```

Скрипт правит смонтированный файл на месте, сохраняя inode, — Xray замечает
изменение за секунды, контейнер не перезапускается. При следующем его
пересоздании Docker возьмёт resolv.conf хоста, где тот же адрес.

### Почему адрес моста, а не 127.0.0.1

Docker при наследовании `resolv.conf` хоста **выбрасывает loopback-адреса**
и подставляет публичные: он не знает, что у контейнера сетевой namespace
хоста и `127.0.0.1` здесь рабочий. Адрес моста он пропускает как есть —
поэтому AGH достаётся контейнерам сам, и **compose трогать не нужно**.

Это не просто удобнее, а единственный рабочий путь.
`docker-compose.override.yml` рядом с remnanode принадлежит стороннему
инструменту `configure-remnanode-tls-mount` (сертификаты Hysteria2):

- чужой файл он трогать отказывается — `Override is not managed by this
  script`, и TLS-часть на такой ноде просто не ставится;
- свой генерирует с нуля и кладёт поверх — дописанная туда секция `dns`
  исчезает при его следующем прогоне.

Третий файл проблему не решает: инструмент запускает compose с явными `-f`,
и любой дополнительный override игнорируется.

Наследие прежнего подхода снимает отдельный скрипт. `install.sh` вызывает его
сам, но на уже стоящей ноде его можно запустить отдельно — контейнеры при
этом не перезапускаются, меняются только файлы:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/dykomenko/adh-fleet/main/node/adh-override-cleanup.sh)
```

Нашу секцию `dns` он убирает, сохраняя остальной файл; файл, который был
целиком нашим, удаляет целиком. Чужую секцию `dns` не трогает — сообщает
и оставляет решать вам. `DRY_RUN=1` — посмотреть, ничего не меняя.

### Запасной резолвер

Вторым адресом в `resolv.conf` идёт публичный DNS, и это обязательно.
С единственным адресом падение AGH оставляет Xray вообще без DNS: клиент
проходит REALITY, сервер принимает соединение и не может отрезолвить адрес
назначения — для клиента это «VPN подключен, но ничего не грузится».

Резолверы опрашиваются по порядку, поэтому при живом AGH весь трафик идёт
через фильтры, а `timeout:1 attempts:1` делает переключение почти незаметным.
Плата — во время аварии AGH реклама не режется. Нужно наоборот, fail-closed
(лучше без интернета, чем без фильтров) — ставьте `AGH_RESOLV_FALLBACK=''`
при установке.

Поправить `resolv.conf` вручную:

```bash
rm -f /etc/resolv.conf
printf 'nameserver 172.17.0.1\nnameserver 1.1.1.1\noptions timeout:1 attempts:1\n' > /etc/resolv.conf
getent hosts example.com
```

Адрес моста сверьте по своей ноде — `ip -4 addr show docker0`. И это должен
быть обычный файл, а не символьная ссылка на `/run/systemd/resolve/resolv.conf`:
пока это ссылка, systemd-resolved перезапишет содержимое.

Если фильтрации нет, надёжнее всего определить причину захватом трафика —
при подключённом клиенте:

```bash
apt-get install -y tcpdump
timeout 25 tcpdump -ni any 'port 53 or port 853' -c 40
```

- запросы на `172.17.0.1.53` — всё правильно, путь через AGH;
- запросы с публичного адреса ноды на `8.8.8.8`, `1.1.1.1` или порт `853` —
  резолвит либо встроенный резолвер Xray (осталась секция `dns`), либо
  контейнер с подставленным Docker'ом публичным адресом. Различить помогает
  `docker exec remnanode cat /etc/resolv.conf`, а соединения на 853-й порт
  указывают именно на Xray: DoT умеет только его встроенный резолвер.

Проверять фильтрацию с личного устройства ненадёжно: локальный блокировщик
в браузере или свой DNS дадут ложноположительный результат. Берите чистое
устройство либо смотрите журнал запросов в панели AGH — там видно, доходят
ли до него клиентские домены.

**WireGuard.** Push-механизма нет, адрес прописывается при генерации конфига:

```ini
[Interface]
Address = 10.107.0.5/32
DNS = 10.107.0.1
```

**OpenVPN:**

```
push "dhcp-option DNS 10.107.0.1"
push "block-outside-dns"
```

`block-outside-dns` нужен Windows-клиентам: без него система продолжит
спрашивать DNS физического интерфейса в обход туннеля.

В обоих туннельных случаях указывайте **один** DNS. Windows и Android
опрашивают перечисленные серверы параллельно, и со вторым «запасным»
фильтрация потечёт постоянно, а не только при аварии.

## Безопасность выходной ноды

Клиент, подключённый к ноде, выходит в интернет с её адреса — а значит может
обратиться и к её внутренним сервисам. Firewall тут не помощник: запросы
приходят изнутри.

Закрывается на стороне Xray. В `routing.rules` первым правилом:

```json
{
  "type": "field",
  "ip": ["geoip:private"],
  "outboundTag": "block"
}
```

Это отсекает клиентам не только панель AGH, но и всё внутреннее на ноде —
Docker-сети, оверлей, метрики, сам `remnanode`.

Проверка с подключённого клиента — все три должны дать таймаут или `000`:

```bash
curl -m 5 -o /dev/null -w "публичный: %{http_code}\n" http://ПУБЛИЧНЫЙ_IP:3000/
curl -m 5 -o /dev/null -w "оверлей:   %{http_code}\n" http://100.x.x.x:3000/
curl -m 5 -o /dev/null -w "localhost: %{http_code}\n" http://127.0.0.1:3000/
```

Случай с `127.0.0.1` самый неочевидный: при настройке клиента через SOCKS
или HTTP-прокси браузер отдаёт адрес прокси как есть, и Xray подключается
к `127.0.0.1:3000` на самой ноде. С её точки зрения это обычное локальное
соединение, которое firewall обязан разрешать — оно нужно синхронизатору
и ssh-туннелю. Поэтому закрывать надо именно правилом Xray.

---

## Убрать ноду из парка

Удалите пир в консоли Netbird. В течение часа он исчезнет из `sync.yaml`,
синхронизатор перезапустится с новым составом. Чистить руками ничего не нужно.

---

## Чего на реплике делать нельзя

**Настраивать фильтры, правила, апстримы и клиентов.** Всё это приезжает
с origin, и любая ручная правка будет затёрта при следующем прогоне.
Единственное место для изменений — origin-нода.

## Если что-то пошло не так

<details>
<summary><b>На ноде уже был установлен Netbird</b></summary>

Самая частая ситуация на VPS с историей. Установщик netbird отказывается
работать на запущенной службе, пишет «NetBird service is running»
и **выходит с кодом успеха**, оставляя старый бинарь. А `netbird up`
на подключённом агенте отвечает «Already connected» и не применяет ни ключ,
ни флаги.

Вдвоём это даёт ноду, которая выглядит полностью исправной, но работает
со старой конфигурацией — иногда в чужой сети.

`install.sh` обрабатывает это сам: останавливает службу до установщика
и сносит `/etc/netbird` и `/var/lib/netbird`. Вручную:

```bash
systemctl stop netbird
curl -fsSL https://pkgs.netbird.io/install.sh | sh
systemctl stop netbird && rm -rf /etc/netbird /var/lib/netbird && systemctl start netbird
netbird up --management-url https://api.netbird.io:443 \
  --setup-key "$NB_KEY_REPLICA" --hostname HK01 \
  --disable-dns --dns-resolver-address 127.0.0.1:5053
```

Старый пир останется в консоли отдельной записью — удалите его.
</details>

<details>
<summary><b>Порт 53 занят, AGH не поднимается</b></summary>

Два возможных виновника. Смотрим, кто именно:

```bash
ss -ulnp | grep ':53 '
```

**`systemd-resolved`** — отключаем stub-listener и переводим `resolv.conf`
на реальные апстримы. Вторая команда обязательна: без неё файл продолжает
указывать на `127.0.0.53`, который больше не слушает, и нода остаётся без
резолвинга — перестают работать `apt`, `docker pull` и сам AGH.

```bash
sed -i 's/^#\?DNSStubListener=.*/DNSStubListener=no/' /etc/systemd/resolved.conf
systemctl restart systemd-resolved
ln -sf /run/systemd/resolve/resolv.conf /etc/resolv.conf
```

**`netbird`** — его локальный резолвер садится на 53-й порт. Одного
`--disable-dns` мало: он лишь запрещает агенту править настройки DNS системы,
а слушатель всё равно поднимается. Уводит его только второй флаг:

```bash
netbird down
netbird up --setup-key "$NB_KEY_REPLICA" --hostname HK01 \
  --disable-dns --dns-resolver-address 127.0.0.1:5053
```

Проверено на netbird 0.78.2.
</details>

<details>
<summary><b>AGH отвечает REFUSED на все запросы</b></summary>

Netbird 0.79 перехватывает DNS на уровне пакетов. В его таблице nftables
появляется цепочка с правилом:

```
udp dport 53 ip daddr 127.0.0.1 dnat to 127.0.0.1:5053
```

Запросы к `127.0.0.1:53` уходят в резолвер самого netbird, а не в AGH, и тот
отказывает всему чужому. Выглядит как «AGH сломался», хотя он исправен:
на любом другом адресе или порту отвечает нормально.

**`--disable-dns` от этого не спасает** — правило ставится и при
`DisableDNS=True`. В 0.78 такой цепочки не было, поэтому необновлённые ноды
работают, а обновлённые нет.

**В 0.80 правила нет вообще.** Ни в nftables, ни в iptables — перехват
делается без них, а снять его нечем. Поэтому бороться с ним мы перестали:
на `127.0.0.1` не указывает ни `resolv.conf`, ни проверки. Все адреса, кроме
этого одного, работают нормально, так что схеме перехват не мешает —
мешает только диагностике, если проверять через `127.0.0.1` по привычке.

Признак, отличающий от всего остального:

```bash
dig @127.0.0.1 google.com +short   # REFUSED
dig @127.0.0.2 google.com +short   # отвечает
```

Перехват ловит только `127.0.0.1`, поэтому запрос к `127.0.0.2` или `::1`
проходит. Это же — быстрый способ отделить проблему AGH от чужого перехвата.

Где перехват сделан правилом nftables (0.79), его снимает юнит `adh-firewall`
при каждой загрузке:

```bash
curl -fsSL https://raw.githubusercontent.com/dykomenko/adh-fleet/main/node/adh-firewall.sh   -o /usr/local/sbin/adh-firewall.sh
chmod 755 /usr/local/sbin/adh-firewall.sh
systemctl restart adh-firewall.service
```

Контейнеры при этом не трогаются.

</details>

<details>
<summary><b>Синхронизатор пишет 401 Unauthorized</b></summary>

Учётки разошлись: на реплике лежит хеш не от того пароля, что в `admin.pass`
на origin. Сравните напрямую, на обеих нодах:

```bash
grep -A2 '^users:' /opt/adguardhome/conf/AdGuardHome.yaml
```

Причины: реплику ставили с неверным `AGH_PASS_HASH` (теперь `install.sh`
такое отклоняет) либо пароль на origin меняли после снятия шаблона.

Починка на реплике — подставить хеш с origin и перезапустить. Кавычки
одинарные, в хеше есть `$`:

```bash
sed -i 's|^    password: .*|    password: ХЕШ_С_ORIGIN|' \
  /opt/adguardhome/conf/AdGuardHome.yaml
docker restart adguardhome
```
</details>

<details>
<summary><b>Нода не появляется в списке реплик на origin</b></summary>

Сначала проверьте, видит ли её origin вообще:

```bash
netbird status | grep -i 'peers count'
```

Ноль пиров — нода не подключилась к оверлею или ушла в другой аккаунт.
Сверьте management-сервер на обеих нодах:

<details>
<summary><b>Файлы скачались пустыми, systemd пишет «Unit file is masked»</b></summary>

Возникает, если писать загруженное через `tee`: при неудачном `curl` файл
всё равно создаётся, только пустым. Юнит нулевой длины systemd считает
замаскированным, и сообщение об ошибке никак не указывает на исходную
причину.

```bash
rm -f /etc/systemd/system/adh-firewall.service /usr/local/sbin/adh-firewall.sh
systemctl daemon-reload
```

Затем повторите загрузку с `-o` и цепочкой через `&&`, как в `install.sh`.
</details>
